\section{Purpose}

This document defines the verification and validation strategy for the Hasnahena platform. The test plan is designed to ensure:
\begin{itemize}
    \item \textbf{Financial Integrity:} All monetary calculations and ledger operations are accurate
    \item \textbf{Role Security:} RBAC enforcement prevents unauthorized actions
    \item \textbf{Workflow Correctness:} Request $\rightarrow$ Process $\rightarrow$ Confirm lifecycle works correctly
    \item \textbf{Compliance:} Shariah compliance and audit trail requirements are met
\end{itemize}

% ------------------------------------------------------------
% TEST SCOPE
% ------------------------------------------------------------
\section{Test Scope}

\subsection{In Scope}
\begin{itemize}
    \item Authentication and authorization mechanisms
    \item Registration and approval workflows
    \item Deposit, withdrawal, loan, repayment, and donation flows
    \item Dispute handling and correction workflows
    \item Audit logging and immutability
    \item API contract validation
    \item Localization (English/Bengali)
    \item Dashboard functionality for all roles
\end{itemize}

\subsection{Out of Scope (Phase 1)}
\begin{itemize}
    \item Mobile application testing
    \item Load/stress testing (deferred to Phase 2)
    \item Third-party payment gateway integration
    \item eKYC/NID API integration testing
\end{itemize}

\section{Priority Test Scenarios}

The following scenarios are considered \critical{} priority due to their impact on financial integrity:

\begin{enumerate}
    \item \textbf{Incorrect Amount Dispute}
    \begin{itemize}
        \item Worker processes wrong amount
        \item Member raises dispute
        \item Admin correction is fully traceable
    \end{itemize}
    
    \item \textbf{Loan Cap Enforcement}
    \begin{itemize}
        \item Personal cap (5× deposit)
        \item Fairness cap (2× pool/members)
        \item Solvency cap (available funds)
        \item Dynamic recalculation on deposit changes
    \end{itemize}
    
    \item \textbf{Default Settlement Waterfall}
    \begin{itemize}
        \item Deduction from borrower deposit
        \item Proportional deduction from guarantors
        \item Charity fund write-off
        \item Residual debt handling
    \end{itemize}
    
    \item \textbf{Withdrawal Blocking}
    \begin{itemize}
        \item Active loan collateral ratio
        \item Active guarantor obligations
        \item Notice period enforcement
    \end{itemize}
    
    \item \textbf{Audit Log Immutability}
    \begin{itemize}
        \item No modification of historical records
        \item Correction operations create new entries
        \item Admin cannot delete audit entries
    \end{itemize}
\end{enumerate}

% ENTRY/EXIT CRITERIA
% ------------------------------------------------------------
\section{Entry and Exit Criteria}

\subsection{Entry Criteria}
Testing may begin when:
\begin{itemize}
    \item Requirements baseline is approved and frozen for sprint
    \item API contracts are documented and versioned
    \item Database schema is deployed to test environment
    \item Test environment is provisioned and accessible
    \item Test data is prepared and loaded
\end{itemize}

\subsection{Exit Criteria}
Testing is complete when:
\begin{itemize}
    \item \textbf{Zero} \critical{} defects remain open
    \item \textbf{Zero} \highsev{} defects in core financial workflows
    \item All priority scenarios pass in staging environment
    \item Regression pass for RBAC and audit log invariants
    \item Test coverage meets minimum threshold (80\% for core modules)
    \item Security scan shows no critical vulnerabilities
\end{itemize}
