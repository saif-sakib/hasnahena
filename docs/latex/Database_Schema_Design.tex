\section{Introduction}

\subsection{Purpose}
This document outlines the high-level Entity-Relationship design for the Hasnahena Core Banking Ledger. The schema is designed to support:
\begin{itemize}
    \item ACID-compliant financial transactions
    \item Double-entry bookkeeping principles
    \item Complete transparency and auditability
    \item Shariah-compliant operations (zero interest)
\end{itemize}

\subsection{Database Selection}
\textbf{PostgreSQL} was selected as the primary database due to:
\begin{itemize}
    \item Strong ACID compliance required for financial operations
    \item Native UUID support for distributed-friendly primary keys
    \item Excellent JSON support for flexible metadata storage
    \item Robust transaction isolation levels
    \item Open-source with enterprise-grade reliability
\end{itemize}

\subsection{Conventions}
\begin{itemize}
    \item All primary keys use \texttt{UUID} type
    \item Timestamps use \texttt{TIMESTAMPTZ} (with timezone)
    \item Monetary values use \texttt{DECIMAL(15,2)} for precision
    \item Soft deletes via \texttt{deleted\_at} column where applicable
    \item All tables include \texttt{created\_at} and \texttt{updated\_at}
\end{itemize}

\section{Security \& Best Practices}

\subsection{Double-Entry Accounting}
Every credit in a member's account has an offsetting debit from a central operational or pool account. This ensures:
\begin{itemize}
    \item Complete traceability of every transaction
    \item Balance verification through debit/credit matching
    \item Regulatory compliance for financial audits
\end{itemize}

\subsection{Immutability}
\begin{itemize}
    \item \textbf{No Updates on Processed Transactions:} Once a transaction reaches CONFIRMED status, UPDATE statements are prohibited at the application level
    \item \textbf{Reversals via Compensation:} Corrections are performed by appending a compensating transaction with negative amount, preserving the original record
    \item \textbf{Audit Log Protection:} The audit\_log table has no UPDATE or DELETE permissions granted to application roles
\end{itemize}

\section{Appendix: Entity Relationship Diagram}

The full ER diagram is maintained separately in the project documentation. Key relationships:

\begin{itemize}
    \item \textbf{User} $\rightarrow$ \textbf{Nominee}: One-to-One (each member has one nominee)
    \item \textbf{User} $\rightarrow$ \textbf{Transaction}: One-to-Many (initiator)
    \item \textbf{User} $\rightarrow$ \textbf{Loan}: One-to-Many (borrower)
    \item \textbf{Loan} $\rightarrow$ \textbf{Guarantor}: One-to-Many
    \item \textbf{User} $\rightarrow$ \textbf{Guarantor}: One-to-Many (guarantor role)
    \item \textbf{User} $\rightarrow$ \textbf{Audit\_Log}: One-to-Many (actor)
\end{itemize}
